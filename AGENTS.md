# AGENTS.md: правила проекта

Этот файл читается в начале каждой задачи. Здесь собраны постоянные правила проекта «Веб-конструктор опросов и тестов». Подробное описание лежит в папке `docs/`.

## 1. О проекте

Веб-приложение, в котором **составитель** создаёт опросы и тесты, а **участник** их проходит. Опросы и тесты хранятся в одних и тех же таблицах (поле `forms.is_test`). У опросов есть блоки и условия показа вопросов (ветвление). У тестов есть баллы, правильные ответы, шкала оценок, ограничение времени. Есть статистика для составителя, библиотека готовых блоков и картинки к вопросам.

Проект создаётся с чистого листа. Автор проекта учится, поэтому код должен быть простым и понятным (см. раздел 5).

## 3. Стек и окружение

- **Бэкенд:** Python, FastAPI, SQLAlchemy, psycopg (версии 3), Alembic, Pydantic, JWT для входа.
- **База данных:** PostgreSQL, установлен локально. **Docker не используем.**
- **Фронтенд:** Vue 3 (Vite, `<script setup>`), Vue Router, Pinia. Для диаграмм статистики позже Chart.js через `vue-chartjs`.
- Настройки (строка подключения к БД, секрет JWT, срок жизни токена) хранятся в `.env`. В репозитории только `.env.example`, реальный `.env` в `.gitignore`.
- Время хранится в UTC.
- Загруженные картинки лежат в папке `backend/uploads/` и раздаются по адресу `/uploads/...`.

## 5. Стиль кода

- **Просто и понятно.** Автор проекта не опытный разработчик. Предпочитай прямой, «скучный» код: явные функции, понятные имена, короткие функции. Не используй сложные паттерны (универсальные репозитории, фабрики фабрик, декораторы-магию, метаклассы, внедрение зависимостей сверх стандартного `Depends` FastAPI).
- **Комментарии на русском** там, где логика не очевидна: объясняй, *зачем* так сделано.
- Имена переменных, функций, таблиц и полей на английском.
- Логику с условиями и баллами выноси в `services/` отдельными функциями без привязки к FastAPI, чтобы её можно было проверить тестами.
- Один роутер на тему, в роутерах только приём запроса, проверка прав, вызов логики и ответ.
- Не добавляй библиотеки, которых нет в списке стека, без объяснения причины.

## 6. Как работать над задачей

- Проект делается **поэтапно**. В каждой задаче сказано, что именно делать. Делай только это и не заходи в следующие этапы.
- Перед началом коротко опиши план (какие файлы будут созданы или изменены).
- Не удаляй и не переписывай то, что не относится к задаче. Не меняй миграции, которые уже созданы и применены: для изменений добавляй новую миграцию.
- Секреты (пароли, ключи) не записывай в код и в репозиторий.
- В конце ответа напиши по-русски: что сделано, список созданных и изменённых файлов, как запустить и как проверить результат, что осталось неясным.
- Если для проверки нужны команды (установка, миграции, запуск), дай их точным списком. Раздел «Как запустить» в `README.md` ведётся и обновляется по мере появления команд.

## 7. Главные правила предметной области

Полные описания в `docs/`. Здесь то, что нельзя нарушать.

**Пользователи.** `users.is_author`: true для составителя, false для участника. Роль задаётся при регистрации и не меняется. Составитель создаёт и редактирует формы, но не проходит чужие. Участник только проходит.

**Булевы поля вместо строк:** `is_author`, `is_test`, `is_published`, `requires_login`, `take_by_blocks`, `allow_free_navigation`, `shuffle_questions`, `shuffle_answer_options`, `show_correct_answers`, `show_results_by_block`, `is_answer_required`, `allow_partial_scoring`, `match_all`, `is_correct`, `is_public`. Поля `status`, `role`, `type`, `access` в формах **не используются**.

**Справочники.** Типы вопросов (`question_types`: `single`, `multiple`, `text`, `info`) и операторы условий (`condition_operators`: `chosen`, `not_chosen`, `equals`, `contains`, `answered`, `not_answered`) лежат в таблицах и заполняются в миграции. В JSON API передаются текстовые коды, сервер сопоставляет их с номерами.

**Формы и доступ.**
- Форма открывается по ссылке со случайным `public_code`.
- `requires_login = false`: форму может пройти и анонимный участник (у попытки `user_id` пустой, он подтверждает попытку заголовком `X-Attempt-Key`).
- `max_attempts` задан только при `requires_login = true`.
- Опубликованную форму (`is_published = true`) редактировать нельзя, для новой версии есть копия.
- При каждом сохранении черновика (`PUT /forms/{id}`) все его блоки, вопросы, варианты, условия и правила получают новые номера; после публикации номера не меняются. Публикация (`POST /forms/{id}/publish`) при проблемах возвращает 422 вида `{"detail": "Форма не прошла проверку", "problems": ["..."]}`. Копия (`POST /forms/{id}/copy`) копирует всё содержимое, кроме попыток, и работает для черновика и опубликованной формы.
- Поле `condition_groups.parent_group_id` зарезервировано под вложенные группы условий и пока не используется.
- Блоки есть у всех форм, у новой формы один пустой блок без названия.
- Составитель сохраняет форму целиком одним запросом `PUT /forms/{id}` (удаляется прежнее содержимое черновика и записывается присланное). В запросе у новых элементов временные ключи (`key`), настоящие номера расставляет сервер.

**Правильные ответы** (`is_correct`, `correct_text_answers`) участнику не отдаются, пока он не завершил тест, и только если включено `show_correct_answers`.

**Условия показа (только опросы).** Условие блока или вопроса ссылается только на **более ранние** вопросы и не на вопросы типа `info`. Правила видимости:
1. ссылки только на более ранние вопросы;
2. скрытый вопрос считается неотвеченным;
3. если скрыт блок, скрыты и его вопросы (блок без видимых вопросов пропускается);
4. видимость вычисляется сверху вниз;
5. ответы на скрытые вопросы отбрасываются, сервер при завершении сам пересчитывает видимость;
6. после сработавшего правила досрочного завершения все последующие вопросы не показаны (см. ниже).

**Досрочное завершение (только опросы).** У вопроса может быть несколько правил `early_finish_rules` (порядок по `position`, срабатывает первое подходящее). У правила есть условие (те же `condition_groups` и `conditions`, связь через `condition_groups.early_finish_rule_id`) и необязательное `message`. Условие правила может ссылаться на вопросы, которые стоят **не позже** вопроса правила (более ранние и сам этот вопрос), но не на `info`. Правило проверяется только у показанного вопроса, когда участник идёт дальше кнопкой «Далее» (в режиме `take_by_blocks`: после блока, правила вопросов блока по порядку). Если правило сработало, попытка завершается: записываются `attempts.early_finish_rule_id` и `finished_at`, последующие вопросы считаются не показанными (строк в `attempt_answers` нет, ответы на них отбрасываются, обязательность у них не проверяется). Сервер при завершении сам просматривает вопросы сверху вниз и определяет сработавшее правило. В тестах правил нет, в библиотеку блоков они не сохраняются.

**Сообщения на странице завершения.** Три необязательных поля: `early_finish_rules.message`, `grading_scale.message` (оценка, полученная в тесте) и `forms.completion_message`. Показывается одно, первое из заполненных в этом порядке; если пусто, стандартный текст «Спасибо за участие!». Простой текст без HTML, до 1000 символов (проверяется в API, в базе тип `text`). В ответе на finish сообщение приходит в поле `message`, а признак досрочного завершения в поле `finished_early`.

**Режимы прохождения** (у опросов и тестов): `take_by_blocks` (страница равна блоку, иначе один вопрос на экране) и `allow_free_navigation` (можно возвращаться и переходить, иначе строго по порядку). Перемешивание делает сервер при старте попытки: `shuffle_answer_options` для опросов и тестов, `shuffle_questions` только для тестов (внутри блока или по всему тесту, в зависимости от `take_by_blocks`).

**Баллы.** Все баллы целые.
- `single` и `text`: полный балл за верный ответ, иначе 0. Текст сравнивается без учёта регистра и лишних пробелов, запятая в числах заменяется точкой.
- `multiple` и `allow_partial_scoring = false`: полный балл только если выбраны ровно все верные варианты.
- `multiple` и `allow_partial_scoring = true`: (верно выбранные − неверно выбранные) / число верных × баллы за вопрос, **округление вниз**, не ниже 0.
- Вопрос типа `info` в баллах и статистике не участвует.
- Процент = `score / max_score × 100`. Оценка берётся из `grading_scale` (наибольшая граница, не превышающая процент); в `attempts` записывается `grading_scale_id`.

**Попытки.** Отдельного поля статуса нет: попытка завершена, если `attempts.finished_at` не пусто. Для каждого показанного вопроса создаётся строка в `attempt_answers` (даже с пустым ответом), для скрытых и `info` строк нет. Тест с ограничением времени сервер принимает с запасом 2 минуты; позже этого срока завершение отклоняется (409), попытка остаётся незавершённой. Лимит `max_attempts` считает все начатые попытки (завершённые и нет): попытка тратится при старте. Ключ анонимной попытки фронтенд хранит в `localStorage`.

**Библиотека блоков.** Работает через копирование. При сохранении в библиотеку создаётся отдельный блок-образец (`blocks.form_id` пусто, `blocks.library_block_id` заполнено); блок в форме о библиотеке не знает. Удаление записи библиотеки удаляет образец (каскад). Блок вставляется только в форму того же типа (`is_test`). По умолчанию `is_public = false`.

**Картинки.** Одна на вопрос (`questions.image_id`), загрузка отдельным запросом `POST /images`, допустимы jpeg, png, webp, gif до 5 МБ, имя файла на сервере случайное.

## 9. Соглашения API

- Формат запросов и ответов JSON (кроме загрузки картинки); адреса и ключи как в `docs/api_description.md`.
- Вход: заголовок `Authorization: Bearer <токен>`. Анонимный участник: `X-Attempt-Key`.
- Ошибки: `{ "detail": "Текст ошибки" }` (иногда с дополнительными полями); коды 401, 403, 404, 409, 413, 422 как в документе.
- Проверки доступа («вошёл ли», «составитель ли», «его ли это форма, попытка или блок») оформляй небольшими отдельными функциями и подключай через `Depends`.
- В ответах даты в формате ISO 8601.

## 10. Не делать сейчас

Совместное редактирование форм, генерацию форм через ИИ, экспорт в CSV, библиотеку отдельных вопросов, картинки в вариантах ответа, видео, Docker, цветные макеты и дизайн. Эти части отложены сознательно.
