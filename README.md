# Конструктор опросов и тестов

Этап 5а: условия показа блоков и вопросов, правила досрочного завершения опросов.
Редактор сохраняет условия и правила; их выполнение участником появится на этапе прохождения.
API: `POST /auth/register`, `POST /auth/login`, `GET /auth/me`, `GET /health`.
Формы: `GET /my/forms`, `POST /forms`, `GET /forms/{id}`, `PUT /forms/{id}`, `DELETE /forms/{id}`.
Документация — `/docs`, файлы — `/uploads`. Публикация и прохождение появятся позже.

## Как запустить

Для этапа 5а новых зависимостей, команд запуска и миграций нет. Тип `info` пока
недоступен в API и редакторе (запланирован на этап 8).

Нужны Python 3.11+, Node.js 22.12+ (или 24 LTS), npm и запущенный PostgreSQL.
Команды ниже предназначены для PowerShell. `createdb` и `psql` должны быть в PATH
(обычно они находятся в `C:\Program Files\PostgreSQL\<версия>\bin`).

## Как проверить

HTTP-тестам нужны запущенный PostgreSQL, применённые миграции и `backend/.env`.
Они используют подключение из `DATABASE_URL`, каждый тест работает во внешней
транзакции с откатом; `commit()` сервиса завершает только SAVEPOINT. Тестовые
пользователи не остаются в базе, существующие записи не меняются. Последовательность
номеров пользователей может увеличиться — пропуски в id нормальны.
Отдельная тестовая база не создаётся. Для токенов тесты используют свой секрет.


### Проверка конструктора

1. Войдите составителем и откройте «Мои формы». Создайте опрос, указав название.
2. Добавьте вопросы трёх типов: один вариант, несколько вариантов, текстовый ответ.
   Добавьте варианты ответа, отметьте обязательность, сохраните и обновите страницу.
3. Проверьте изменение названия и описания, удаление вопросов и вариантов, повторное
   сохранение. Пустые тексты вопросов и неполные списки вариантов допустимы в черновике.
4. Создайте тест: обязательность вопроса не отображается. Укажите баллы и верные ответы,
   для нескольких ответов включите частичные баллы. Для текстового вопроса добавьте
   допустимые ответы. Проверьте пересчёт «Всего баллов» и очистку данных при смене типа.
5. В списке проверьте фильтры типа и статуса, отмену удаления и подтверждение удаления.
6. Участнику редактор недоступен. Чужая форма даёт 403, отсутствующая — 404.
   Для опубликованной формы редактор доступен только для чтения, PUT возвращает 409.
   Публикации через интерфейс на этом этапе нет.

Редактор показывает все блоки; API сохраняет порядок переданных блоков, вопросов
и вариантов. Все настройки формы сохраняются при редактировании. Сохранение
заменяет содержимое черновика в одной транзакции; при ошибке прежнее содержимое остаётся.
Тесты backend проверяют также откат, права, коллизию публичного кода и каскадное удаление
без изменения библиотеки. Новых зависимостей и миграций на этом этапе нет.

### Проверка условий и правил завершения (этап 5а)

1. Создайте опрос с двумя блоками. В первом добавьте вопросы с выбором и текстовый,
   во втором — ещё один вопрос.
2. Задайте условие второго блока по вопросу первого. У вопроса задайте несколько
   условий и переключите «Все условия» / «Любое из условий». Проверьте выбор
   вариантов и текстовые операторы.
3. Добавьте два правила завершения с сообщениями. В условии правила доступен
   сам вопрос. Поменяйте правила стрелками, сохраните и обновите страницу:
   сообщения, порядок правил и ссылки должны сохраниться.
4. Попробуйте переместить вопрос или блок так, чтобы зависимость оказалась ниже,
   удалить вопрос или вариант со ссылками, изменить тип single на text при условии
   «Выбран вариант». Действие блокируется, сообщение перечисляет зависимые места.
   После удаления ссылок действие разрешено. Ссылки внутри удаляемого блока
   не мешают его удалению; внешние — мешают.
5. У теста нет редакторов условий и правил. API отклоняет эти поля, даже если
   `condition = null` или `finish_rules = []`; фронтенд их для теста не отправляет.

Смена типа блокируется без дополнительного диалога, если нарушает существующие
условия; совместимые изменения разрешены (например, single → multiple).
Проверяются сохранение и редактирование правил, но не их выполнение участником.
Все проверки запускаются обычными `pytest` и `node --test src/utils/*.test.js`
(точные команды выше). Сервер берёт операторы из справочника, а позиции правил
назначает по порядку списка. Проверка `info` тестируется напрямую в функциях,
существующий запрет этого типа в API сохранён.

### Проверка блоков и несохранённых изменений (этап 4б)

1. Добавьте три блока, один оставьте пустым. Задайте названия и добавьте вопросы
   в разные блоки. Вопросы нумеруются сквозным списком, баллы суммируются по всей форме.
2. Перемещайте блоки и вопросы стрелками. Крайний вопрос блока переходит только
   в соседний блок: пустые блоки не пропускаются, исходный блок не удаляется.
   Проверьте цепочку из двух пустых блоков перед блоком с единственным вопросом.
3. Непустой блок удаляется после подтверждения с числом вопросов, пустой — сразу.
   Единственный блок удалить нельзя. Пустое название сохраняется как null,
   пробелы по краям обрезаются, больше 255 символов даёт 422.
4. Сохраните и обновите страницу: названия, порядок и принадлежность вопросов
   блокам должны остаться. Прокрутите длинную форму: верхняя панель остаётся видна.
5. Измените название или любое другое поле: появляется «Есть несохранённые изменения».
   Верните прежнее значение — отметка исчезает. После сохранения видно «Сохранено».
6. При несохранённых изменениях проверьте «К списку», другую ссылку, кнопку браузера
   «Назад» и «Выйти». «Остаться» сохраняет редактор и вход в аккаунт;
   «Уйти без сохранения» разрешает переход. Ошибка сохранения не снимает отметку.
7. В обычном браузере измените поле и обновите страницу: должно появиться стандартное
   предупреждение браузера. После сохранения и у опубликованной формы его нет.
   Для появления стандартного окна браузеру нужно предварительное действие пользователя.

Тесты функций перемещения и снимков входят в `node --test src/utils/*.test.js`.
Тесты backend проверяют три блока, перенос вопросов, позиции, названия и откат
после ошибки вставки второго блока. На этом этапе новых зависимостей и миграций нет.

### Проверка настроек, баллов и шкалы (этап 4а)

1. В настройках выберите доступ только авторизованным и максимум попыток. При выборе
   «Всем» максимум попыток очищается. Проверьте режимы прохождения, перемешивание
   вариантов и сообщение завершения со счётчиком символов.
2. У теста задайте время, перемешивание вопросов и настройки показа результатов.
   Сохраните, обновите страницу и проверьте, что все значения остались.
3. При первом открытии теста с пустой шкалой редактор подставляет 0/50/70/85% и оценки
   2/3/4/5. Сервер создаёт эти строки только при сохранении. Можно удалить всю шкалу;
   при следующем открытии редактор снова предложит стандартную.
4. В Swagger проверьте GET и PUT `/forms/{id}`: баллы 1–1000, не больше одного верного
   варианта у single, допустимые ответы у text, шкалу с уникальными границами 0–100%.
   Непустая шкала должна содержать 0%. Пустая шкала допустима.
5. Попытки ограничиваются числом 1–1000, время — 1–1440 минутами (или null).
   Нулевые баллы, два верных варианта у single, шкала без 0% и заполненные поля теста
   у опроса дают 422. Ошибки отображаются над редактором.
6. Повторно сохраните другие допустимые ответы и шкалу: старые строки заменяются.
   Автотесты проверяют замену и откат всей транзакции при ошибке вставки шкалы.

Вопросы старых тестов с `points = null` получают в редакторе 1 балл; GET оставляет null
до сохранения. Допустимые ответы обрезаются по краям, пустые удаляются, повторы
без учёта регистра и лишних пробелов объединяются. Лимит API — 255 символов,
существующий столбец `answer_text` остаётся `varchar(500)`. Порядок ответов хранится
порядком вставки и восстанавливается по `id` (отдельного `position` в таблице нет).

Согласованное расхождение с `docs/api_description.md`, раздел 3.2, ошибки PUT:
текстовый вопрос без допустимых ответов можно сохранить в черновике. Проверка полноты
перенесена на публикацию (этап 5). Проверка прохождения и подсчёт баллов участника
пока не реализованы. Новых зависимостей и миграций нет.

### Проверка регистрации и входа

1. В [Swagger UI](http://localhost:8000/docs) выполните `POST /auth/register`
   с новым email, именем, паролем и `is_author: true` или `false`: ожидается 201.
   Повторный email даёт 409; неверные данные — 422 с русским текстом в `detail`.
2. Выполните `POST /auth/login`. Скопируйте `access_token`, нажмите **Authorize**
   и вставьте сам токен (без слова Bearer). `GET /auth/me` вернёт пользователя;
   без токена — 401. В ответах не должно быть `password_hash`.
3. На [фронтенде](http://localhost:5173) зарегистрируйте составителя и участника
   с разными email. Проверьте автоматический вход, выход, повторный вход и обновление страницы.
4. Гостем откройте `/my/forms`: откроется вход с `redirect`. После входа составителем
   вернётесь туда. Для участника `/my/forms` покажет «Нет доступа», для составителя
   то же произойдёт на `/my/attempts`. Неизвестный адрес покажет «Не найдено».
5. На регистрации проверьте короткий пароль, слишком длинный пароль, несовпадение
   повторного пароля и занятый email. Подсказка «Не менее 8 символов» видна постоянно.
   При входе неверный пароль любой длины даёт 401.

Пароль: минимум 8 символов Unicode, максимум 72 байта UTF-8; разрешены кириллица
и эмодзи. Пробелы сохраняются, обрезки нет. 36 русских букв или 18 обычных эмодзи
занимают ровно 72 байта. В интерфейсе и ошибках API единица «байт» не используется.
Токен хранится в localStorage; при его недействительности удаляется. Если браузер
запретил localStorage, вход работает в памяти до обновления страницы.

Добавлены `bcrypt` для хеширования паролей, `PyJWT` для подписи и проверки JWT,
`email-validator` для проверки email в Pydantic. `app/dependencies.py` содержит
общие проверки пользователя и роли через Depends; файл добавлен в структуру AGENTS.md.

## Согласованные решения

- Все ссылки на `users` используют `ON DELETE RESTRICT`; удаления пользователей в API нет.
- `questions.image_id` и `attempts.grading_scale_id` используют `SET NULL`.
  Ссылки на тип вопроса и оператор условия — `RESTRICT`.
  Остальные внешние ключи — `CASCADE`: удаляются принадлежащие родителю записи,
  ссылки ответов на удалённые вопросы/варианты и связанные условия.
- Все булевы поля — `NOT NULL`, по умолчанию `false`, кроме `condition_groups.match_all = true`.
- `created_at` получает UTC на стороне PostgreSQL: `timezone('utc', now())`.
  Тип остаётся `timestamp without time zone`, как в схеме; даты, задаваемые приложением,
  также нужно передавать в UTC. Для других дат автоматическое значение не задано.
- `blocks` проверяет, что заполнено ровно одно из `form_id` и `library_block_id`.
- Во второй миграции обновлён `ck_condition_groups_owner`: у верхней группы заполнено
  ровно одно из `block_id`, `question_id`, `early_finish_rule_id`, у вложенной — все три пусты.
- Список nullable-полей отдельно согласован с пользователем:
  `forms.description`, `forms.max_attempts`, `forms.time_limit_minutes`, `forms.published_at`,
  `blocks.title`, `blocks.form_id`, `blocks.library_block_id`, `questions.points`,
  `questions.image_id`, `library_blocks.description`, `attempts.user_id`,
  `attempts.finished_at`, `attempts.score`, `attempts.max_score`, `attempts.percent`,
  `attempts.grading_scale_id`, `attempt_answers.text_answer`, `attempt_answers.score`,
  `conditions.choice_id`, `conditions.text_answer`, `condition_groups.parent_group_id`,
  `condition_groups.block_id`, `condition_groups.question_id`. Остальные поля — `NOT NULL`.
- Созданы восемь явно перечисленных в схеме индексов и индекс
