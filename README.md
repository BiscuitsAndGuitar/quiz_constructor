# Конструктор опросов и тестов

Этап 8а: картинки к вопросам и тип «Текст без вопроса» (`info`) в конструкторе,
прохождении и предпросмотре. Статистика составителя доступна на `/forms/:id/stats`.
API: `POST /auth/register`, `POST /auth/login`, `GET /auth/me`, `GET /health`.
Формы: `GET /my/forms`, `POST /forms`, `GET /forms/{id}`, `PUT /forms/{id}`, `DELETE /forms/{id}`.
Публикация: `POST /forms/{id}/publish`. Копия: `POST /forms/{id}/copy`.
Картинки: `POST /images` (multipart/form-data, поле `file`, только составитель).
Прохождение: `GET /public/forms/{code}`, `POST /forms/{id}/attempts`,
`POST /attempts/{id}/finish`, `GET /attempts/{id}/result`, `GET /my/attempts`.
Статистика составителя: `GET /forms/{id}/attempts`, `GET /attempts/{id}/details`,
`GET /forms/{id}/stats`. Все три запроса доступны только владельцу формы.
Документация — `/docs`, файлы — `/uploads`. Страницы участника: `/f/:code`,
`/attempt/:id`, `/attempt/:id/result`, `/my/attempts`. Предпросмотр открывается
без отдельного адреса, не создаёт попытку и не отправляет запросы API.

## Работа с backend и frontend отдельно

### Проверка прохождения в браузере (6б)

1. Запустите оба сервера. Под составителем создайте и опубликуйте опрос и тест,
   скопируйте ссылки. Откройте их в другом браузере или после выхода из аккаунта.
2. Проверьте открытый опрос анонимно и форму с обязательным входом: кнопки входа
   и регистрации должны возвращать на исходную форму. Составитель видит запрет.
3. Проверьте четыре сочетания «Проходить по блокам» и «Свободная навигация»
   на отдельных опубликованных формах. Скрытые вопросы и блоки пропускаются,
   обязательные вопросы опроса подсвечиваются при переходе вперёд.
4. Введите ответы, обновите страницу (подтвердив предупреждение браузера):
   ответы, текущая страница и оставшееся время восстанавливаются. При переходе
   по внутренней ссылке появляется подтверждение выхода.
5. Проверьте изменение раннего ответа и появление/скрытие зависимых вопросов.
   Правило завершения действует по кнопке перехода; в режиме блоков сохраняются
   показанные ответы всего текущего блока, следующие блоки отбрасываются.
6. У теста задайте лимит 1 минуту, дождитесь автоматической отправки. Проверьте
   подтверждение ручного завершения с пропусками и результат: баллы, оценку,
   сообщения, таблицу блоков и разбор с текстами вариантов (если включены).
7. Обновите страницу результата: она загружается с сервера. При исчерпанном
   лимите новая попытка недоступна. «Мои прохождения» открывает историю участника.

Состояние попытки хранится в `sessionStorage`, ключ — в `localStorage`.
При завершении или истечении таймера состояние удаляется; ключ остаётся для
просмотра результата. После истечения таймера при ошибке сети можно повторить
отправку из памяти открытой страницы, не редактируя ответы. После обновления
такой страницы ответы уже не восстанавливаются. До старта проверяется доступность
хранилищ браузера. Серверные ответы `review` для выбора дополнены `your_options`
и `correct_options` (объекты с `id` и `text`, порядок формы).

### Проверка статистики через Swagger (7а)

1. Откройте `http://localhost:8000/docs`. Через `POST /auth/login` получите токен
   составителя, укажите его в Authorize. Создайте тест через `POST /forms`,
   сохраните `PUT /forms/{id}`: два блока, single на 1 балл с одним верным
   вариантом и text на 1 балл с допустимым ответом «Да». Укажите шкалу
   0% — «2», 50% — «3», 100% — «5», доступ всем, без лимита попыток и времени.
   Формат тела PUT можно взять из GET формы, созданной в конструкторе.
2. До публикации вызовите `GET /forms/{id}/stats`: вопросы и шкала присутствуют
   с нулевыми показателями, средние значения и медиана null, список дней пустой.
   Затем выполните `POST /forms/{id}/publish`.
3. Уберите токен составителя (Logout в Authorize) и трижды вызовите
   `POST /forms/{id}/attempts`. Сохраните номера и ключи попыток. Для первой
   отправьте оба правильных ответа в `POST /attempts/{id}/finish`, для второй —
   только правильный single, третью не завершайте. В каждом finish передавайте
   соответствующий ключ в `X-Attempt-Key`; номера вопросов и вариантов берите
   из ответа старта. Для авторизованной попытки используйте токен участника.
4. Снова авторизуйтесь составителем. `GET /forms/{id}/attempts` вернёт три строки,
   новые сверху; у незавершённой баллы и оценка null. В `/stats` ожидаются
   started=3, finished=2, completion_percent=66.7, avg_score=1.5, avg_percent=75.
   В шкале: «2» — 0, «3» — 1, «5» — 1. По блокам: 100% и 50%; у text shown=2,
   skipped=1, correct_percent=50, top_answers содержит «да» с count=1.
5. `GET /attempts/{id}/details` завершённой попытки покажет вопросы по порядку
   формы, тексты выбранных вариантов и баллы. У незавершённой answers=[].
6. Создайте опрос с single «Да/Нет», правилом завершения при «Да» и последующим
   необязательным text. Опубликуйте, пройдите анонимно дважды: «Да» и «Нет»
   (text оставьте пустым). Под составителем в `/stats` ожидаются finished=2,
   finished_early=1, одно правило с count=1; у вопросов shown=2 и shown=1,
   у text skipped=1. Баллы, шкала и блоки null, поля правильности отсутствуют.
   В details досрочной попытки будет только первый вопрос и finished_early=true.
7. Без токена эти три запроса дают 401; участнику и другому составителю — 403;
   для несуществующей формы или попытки под составителем — 404.

Статистика учитывает только завершённые попытки, кроме summary.started.
Округление — до одного десятичного знака (половина округляется вверх); медиана
времени округляется вниз до целых секунд. Дни считаются по UTC с заполнением
пропусков нулями. Без завершений структура вопросов, шкалы теста и его блоков
сохраняется с нулями; средние значения и медиана null. Выборки из БД отделены
в `services/statistics_data.py`, чистые расчёты — в `services/statistics.py`.

## Как проверить

HTTP-тестам нужны запущенный PostgreSQL, применённые миграции и `backend/.env`.
Они используют подключение из `DATABASE_URL`, каждый тест работает во внешней
транзакции с откатом; `commit()` сервиса завершает только SAVEPOINT. Тестовые
пользователи не остаются в базе, существующие записи не меняются. Последовательность
номеров пользователей может увеличиться — пропуски в id нормальны.

   Публикация доступна после сохранения черновика.

Редактор показывает все блоки; API сохраняет порядок переданных блоков, вопросов
и вариантов. Все настройки формы сохраняются при редактировании. Сохранение
заменяет содержимое черновика в одной транзакции; при ошибке прежнее содержимое остаётся.
Тесты backend проверяют также откат, права, коллизию публичного кода и каскадное удаление
без изменения библиотеки. Новых зависимостей и миграций на этом этапе нет.

### Проверка серверного прохождения через Swagger (этап 6а)

Откройте `http://localhost:8000/docs` после запуска backend.

1. Войдите составителем через `POST /auth/login`, вставьте токен в Authorize.
   Создайте и сохраните форму через существующий конструктор или POST/PUT,
   затем опубликуйте её. Запомните `id` и `public_code`.
2. Выполните `GET /public/forms/{code}`. Здесь только общая информация.
   Снимите авторизацию составителя: составителю старт запрещён (403).
3. Для формы без входа оставьте Swagger без токена. Для защищённой формы
   зарегистрируйте участника (`is_author: false`), войдите и укажите его токен.
4. Выполните `POST /forms/{id}/attempts`. Сохраните `attempt.id`, `attempt_key`
   и номера вопросов/вариантов из ответа. `question_order` задаёт общий порядок
   вопросов; `deadline` — срок без двухминутного запаса. Правильных ответов,
   баллов и сообщений завершения в ответе старта нет.
5. В `POST /attempts/{id}/finish` отправьте, например:

   ```json
   {"answers": [{"question_id": 101, "option_ids": [301]}, {"question_id": 102, "text": "Москва"}]}
   ```

   Подставьте реальные номера. Для анонимной попытки заполните `X-Attempt-Key`;
   для авторизованной используйте токен владельца (ключ его не заменяет).
6. Проверьте незаполненный обязательный вопрос опроса: 422 с
   `missing_question_ids`, попытка остаётся незавершённой. Ответьте и повторите:
   скрытые вопросы и вопросы после досрочного завершения не сохраняются.
   В режиме по блокам сохраняются видимые вопросы всего блока с правилом.
7. Для теста проверьте баллы, оценку и сообщение. `review` зависит от
   `show_correct_answers`, `block_results` — от `show_results_by_block` и наличия
   двух блоков. Повторный finish возвращает 409.
8. `GET /attempts/{id}/result` возвращает результат, у опроса дополнительно
   `answers`. До завершения — 409. `GET /my/attempts` с токеном участника
   показывает все его попытки, сначала новые; анонимные туда не попадают.

Лимит учитывает все начатые попытки. Позже лимита времени + 2 минуты finish
возвращает 409 без завершения. В тестах время подменяется через `now_utc()`.
Оценка выбирается без округления, процент округляется до двух знаков (половина
вверх). При `max_score = 0` процент 0, оценки нет; сравнение с другими попытками
выполняется обычным образом. При менее пяти других завершённых попыток оно null.
Повторные номера вариантов multiple считаются одним выбором. Значения скрытых
ответов отбрасываются; чужие и повторные question_id возвращают 422.
Сервис `survey_answers` пригоден для будущего просмотра ответов составителем.

### Проверка публикации и копирования (этап 5б)

1. Откройте черновик, измените поле и нажмите «Опубликовать»: появится
   «Сначала сохраните изменения». Сохраните форму и повторите действие.
2. Подтвердите публикацию неполной формы. Все проблемы должны появиться списком
   в окне сообщения. Номера вопросов сквозные по блокам. Исправьте ошибки и сохраните.
3. Опубликуйте опрос или тест: появятся пометка о публикации, ссылка и кнопка копии.
   Поля недоступны, кнопок изменения нет; сворачивание всех разделов продолжает работать.
4. Скопируйте ссылку. Если буфер обмена недоступен, ссылка показана для ручного
   копирования. `/f/:code` пока показывает «Не найдено» — это ожидаемо до этапа 6.
5. Нажмите «Создать копию для редактирования». Откроется новый черновик с новым
   кодом, настройками и содержимым оригинала. Правка копии не меняет оригинал.
6. В списке форм проверьте «Открыть» у опубликованных, «Редактировать» у черновиков,
   «Копия» у всех и «Скопировать ссылку» у опубликованных. После копии список обновляется
   и появляется сообщение с названием. Удаление опубликованной формы также работает.

Проверки публикации ограничены наличием вопросов, двух вариантов для single/multiple,
правильного ответа и положительных целых баллов в тесте. Новых проверок текста нет.
При копировании сохраняются ссылки на картинки, но не попытки и ответы участников.

### Проверка условий и правил завершения (этап 5а)

В конструкторе можно сворачивать отдельные блоки/вопросы или все карточки сразу.
Сворачивание не меняет форму и не требует сохранения; после перезагрузки всё раскрыто.
В свёрнутых карточках доступны перемещение и удаление, видны пометки условий и правил.
Ошибки действий и сохранения показываются в окне: закройте его кнопкой «Понятно»,
крестиком, Esc или щелчком по затемнённому фону. Если ошибка содержит номер блока
или вопроса, раскрываются все карточки (нумерация в серверных ошибках неоднородна).

1. Создайте опрос с двумя блоками. В первом добавьте вопросы с выбором и текстовый,
   во втором — ещё один вопрос.
2. Задайте условие второго блока по вопросу первого. У вопроса задайте несколько
   условий и переключите «Все условия» / «Любое из условий». Проверьте выбор
   вариантов и текстовые операторы.
3. Добавьте два правила завершения с сообщениями. В условии правила доступен
   сам вопрос. Поменяйте правила стрелками, сохраните и обновите страницу:
   сообщения, порядок правил и ссылки должны сохраниться.
4. Попробуйте переместить вопрос или блок так, чтобы зависимость оказалась ниже,
   удалить вопрос или вариант со ссылками, изменить тип single на text при условии
   «Выбран вариант». Действие блокируется, сообщение перечисляет зависимые места.
   После удаления ссылок действие разрешено. Ссылки внутри удаляемого блока
   не мешают его удалению; внешние — мешают.
5. У теста нет редакторов условий и правил. API отклоняет эти поля, даже если
   `condition = null` или `finish_rules = []`; фронтенд их для теста не отправляет.

Смена типа блокируется без дополнительного диалога, если нарушает существующие
условия; совместимые изменения разрешены (например, single → multiple).
Проверяются сохранение и редактирование правил, но не их выполнение участником.
Все проверки запускаются обычными `pytest` и `node --test src/utils/*.test.js`
(точные команды выше). Сервер берёт операторы из справочника, а позиции правил
назначает по порядку списка. Проверка `info` тестируется напрямую в функциях,
существующий запрет этого типа в API сохранён.

### Проверка блоков и несохранённых изменений (этап 4б)

1. Добавьте три блока, один оставьте пустым. Задайте названия и добавьте вопросы
   в разные блоки. Вопросы нумеруются сквозным списком, баллы суммируются по всей форме.
2. Перемещайте блоки и вопросы стрелками. Крайний вопрос блока переходит только
   в соседний блок: пустые блоки не пропускаются, исходный блок не удаляется.
   Проверьте цепочку из двух пустых блоков перед блоком с единственным вопросом.
3. Непустой блок удаляется после подтверждения с числом вопросов, пустой — сразу.
   Единственный блок удалить нельзя. Пустое название сохраняется как null,
   пробелы по краям обрезаются, больше 255 символов даёт 422.
4. Сохраните и обновите страницу: названия, порядок и принадлежность вопросов
   блокам должны остаться. Прокрутите длинную форму: верхняя панель остаётся видна.
5. Измените название или любое другое поле: появляется «Есть несохранённые изменения».
   Верните прежнее значение — отметка исчезает. После сохранения видно «Сохранено».
6. При несохранённых изменениях проверьте «К списку», другую ссылку, кнопку браузера
   «Назад» и «Выйти». «Остаться» сохраняет редактор и вход в аккаунт;
   «Уйти без сохранения» разрешает переход. Ошибка сохранения не снимает отметку.
7. В обычном браузере измените поле и обновите страницу: должно появиться стандартное
   предупреждение браузера. После сохранения и у опубликованной формы его нет.
   Для появления стандартного окна браузеру нужно предварительное действие пользователя.

Тесты функций перемещения и снимков входят в `node --test src/utils/*.test.js`.
Тесты backend проверяют три блока, перенос вопросов, позиции, названия и откат
после ошибки вставки второго блока. На этом этапе новых зависимостей и миграций нет.

### Проверка настроек, баллов и шкалы (этап 4а)

1. В настройках выберите доступ только авторизованным и максимум попыток. При выборе
   «Всем» максимум попыток очищается. Проверьте режимы прохождения, перемешивание
   вариантов и сообщение завершения со счётчиком символов.
2. У теста задайте время, перемешивание вопросов и настройки показа результатов.
   Сохраните, обновите страницу и проверьте, что все значения остались.
3. При первом открытии теста с пустой шкалой редактор подставляет 0/50/70/85% и оценки
   2/3/4/5. Сервер создаёт эти строки только при сохранении. Можно удалить всю шкалу;
   при следующем открытии редактор снова предложит стандартную.
4. В Swagger проверьте GET и PUT `/forms/{id}`: баллы 1–1000, не больше одного верного
   варианта у single, допустимые ответы у text, шкалу с уникальными границами 0–100%.
   Непустая шкала должна содержать 0%. Пустая шкала допустима.
5. Попытки ограничиваются числом 1–1000, время — 1–1440 минутами (или null).
   Нулевые баллы, два верных варианта у single, шкала без 0% и заполненные поля теста
   у опроса дают 422. Ошибки отображаются над редактором.
6. Повторно сохраните другие допустимые ответы и шкалу: старые строки заменяются.
   Автотесты проверяют замену и откат всей транзакции при ошибке вставки шкалы.

Вопросы старых тестов с `points = null` получают в редакторе 1 балл; GET оставляет null
до сохранения. Допустимые ответы обрезаются по краям, пустые удаляются, повторы
без учёта регистра и лишних пробелов объединяются. Лимит API — 255 символов,
существующий столбец `answer_text` остаётся `varchar(500)`. Порядок ответов хранится
порядком вставки и восстанавливается по `id` (отдельного `position` в таблице нет).

Согласованное расхождение с `docs/api_description.md`, раздел 3.2, ошибки PUT:
текстовый вопрос без допустимых ответов можно сохранить в черновике. Проверка полноты
перенесена на публикацию (этап 5). Проверка прохождения и подсчёт баллов участника
пока не реализованы. Новых зависимостей и миграций нет.

### Проверка регистрации и входа

1. В [Swagger UI](http://localhost:8000/docs) выполните `POST /auth/register`
   с новым email, именем, паролем и `is_author: true` или `false`: ожидается 201.
   Повторный email даёт 409; неверные данные — 422 с русским текстом в `detail`.
2. Выполните `POST /auth/login`. Скопируйте `access_token`, нажмите **Authorize**
   и вставьте сам токен (без слова Bearer). `GET /auth/me` вернёт пользователя;
   без токена — 401. В ответах не должно быть `password_hash`.
3. На [фронтенде](http://localhost:5173) зарегистрируйте составителя и участника
   с разными email. Проверьте автоматический вход, выход, повторный вход и обновление страницы.
4. Гостем откройте `/my/forms`: откроется вход с `redirect`. После входа составителем
   вернётесь туда. Для участника `/my/forms` покажет «Нет доступа», для составителя
   то же произойдёт на `/my/attempts`. Неизвестный адрес покажет «Не найдено».
5. На регистрации проверьте короткий пароль, слишком длинный пароль, несовпадение
   повторного пароля и занятый email. Подсказка «Не менее 8 символов» видна постоянно.
   При входе неверный пароль любой длины даёт 401.

Пароль: минимум 8 символов Unicode, максимум 72 байта UTF-8; разрешены кириллица
и эмодзи. Пробелы сохраняются, обрезки нет. 36 русских букв или 18 обычных эмодзи
занимают ровно 72 байта. В интерфейсе и ошибках API единица «байт» не используется.
Токен хранится в localStorage; при его недействительности удаляется. Если браузер
запретил localStorage, вход работает в памяти до обновления страницы.

Добавлены `bcrypt` для хеширования паролей, `PyJWT` для подписи и проверки JWT,
`email-validator` для проверки email в Pydantic. `app/dependencies.py` содержит
общие проверки пользователя и роли через Depends; файл добавлен в структуру AGENTS.md.

После создания базы и применения миграции:

```powershell
psql -h localhost -p 5432 -U postgres -d quiz_constructor -c 'SELECT * FROM question_types;'
psql -h localhost -p 5432 -U postgres -d quiz_constructor -c 'SELECT * FROM condition_operators;'
```

Ожидаются 20 таблиц вместе с `alembic_version`, 4 строки типов и 6 строк операторов.

Откат второй миграции удаляет правила досрочного завершения, их группы и условия,
а также новые поля сообщений и ссылки на правила. Прежние группы показа сохраняются.

## Согласованные решения

- Все ссылки на `users` используют `ON DELETE RESTRICT`; удаления пользователей в API нет.
- `questions.image_id` и `attempts.grading_scale_id` используют `SET NULL`.
  Ссылки на тип вопроса и оператор условия — `RESTRICT`.
  Остальные внешние ключи — `CASCADE`: удаляются принадлежащие родителю записи,
  ссылки ответов на удалённые вопросы/варианты и связанные условия.
- Все булевы поля — `NOT NULL`, по умолчанию `false`, кроме `condition_groups.match_all = true`.
- `created_at` получает UTC на стороне PostgreSQL: `timezone('utc', now())`.
  Тип остаётся `timestamp without time zone`, как в схеме; даты, задаваемые приложением,
  также нужно передавать в UTC. Для других дат автоматическое значение не задано.
- `blocks` проверяет, что заполнено ровно одно из `form_id` и `library_block_id`.
- Во второй миграции обновлён `ck_condition_groups_owner`: у верхней группы заполнено
  ровно одно из `block_id`, `question_id`, `early_finish_rule_id`, у вложенной — все три пусты.
- Список nullable-полей отдельно согласован с пользователем:
  `forms.description`, `forms.max_attempts`, `forms.time_limit_minutes`, `forms.published_at`,
  `blocks.title`, `blocks.form_id`, `blocks.library_block_id`, `questions.points`,
  `questions.image_id`, `library_blocks.description`, `attempts.user_id`,
  `attempts.finished_at`, `attempts.score`, `attempts.max_score`, `attempts.percent`,
  `attempts.grading_scale_id`, `attempt_answers.text_answer`, `attempt_answers.score`,
  `conditions.choice_id`, `conditions.text_answer`, `condition_groups.parent_group_id`,
  `condition_groups.block_id`, `condition_groups.question_id`. Остальные поля — `NOT NULL`.
- Созданы восемь явно перечисленных в схеме индексов и индекс
  `early_finish_rules.question_id`, согласованный в доработке этапа 1.
  PostgreSQL также создаёт индексы для первичных ключей и UNIQUE.
- Реализовано сохранение черновиков с настройками, баллами, правильными ответами
  и шкалой, условиями показа и правилами завершения, публикация и копирование.
  Серверное прохождение, экран участника, история и предпросмотр реализованы.
